v3.0 expands BoB's Reputation Audit from "Google Maps API + TripAdvisor scrape + operator input" (v2.0) to a **5-source factual mesh** by adding:

1. **Deeper Google Places fields** (opening hours, business status, price level, geolocation, service flags) — pure factual, low fabrication risk.

### Candidate 2.3 — Competition Scan (NEW)

**Concept:** Google Places Nearby Search with `radius=1600m` (1 mile) + `type` filter (`bar` | `restaurant` | `night_club` | `cafe` | `lodging`). Pull top 5 by `user_ratings_total`. For each: `name`, `rating`, `user_ratings_total`, `price_level`, `place_id`.

**Cost:** Nearby Search = $32/1000 calls. Place Details for each of 5 competitors = 5 × $17/1000 = $85/1000 audits. Total **~$0.12 per competitive scan**.

**Fabrication risk:** **LOW for numeric output, HIGH if LLM is asked to characterize "why".**

**Output rule (mandatory):**

```
✅ ALLOWED:
"Your venue: 4.6 / 120 reviews / price $$.
Top 5 nearest similar venues:
  1. [Name] — 4.2 / 80 reviews / $$ (320m)
  2. [Name] — 4.4 / 95 reviews / $$$ (450m)
  …
Your rating: above-average. Your review volume: below-average."

❌ FORBIDDEN (this is the new fabrication vector):
"Competitor [Name] is doing better because they have a more diverse menu…"
"You should match Competitor X's pricing strategy…"
"Competitor Y's online presence is stronger because…"
```

The **structural enforcement**: competition module output template has **no free-text "analysis" field**. Only:
1. Numeric table (5 rows).
2. Two derived sentences: rating-vs-average + volume-vs-average.
3. One optional sentence per row labeled `OBSERVATION` containing **only** API-returned facts (e.g., "Has 3 photos uploaded since Jan 2026" — factual, not interpretive).

**Recommendation:** **YES — STRONG**. Highest operator-value-per-fabrication-risk in the entire v3.0 set.

### Candidate 2.5 — SWOT Output Structure

**Tension identified:** SWOT is operator-recognizable (consultants use it) BUT four fixed boxes create **format pressure** — model invents content to fill boxes, especially the harder-to-source "Opportunities" and "Threats."

**Proposal — "Evidence-First" structure, not literal SWOT:**

```
📊 STRENGTHS (each bullet REQUIRES inline source citation)
  • [Operator-verifiable fact] — source: [Google Reviews | TripAdvisor | Operator-input]
  • …

🩹 WEAKNESSES (each bullet REQUIRES inline source citation)
  • [Operator-verifiable critical-review pattern OR operator-stated pain] — source: …
  • …

📡 SIGNALS (replaces "Opportunities" + "Threats")
  • [Factual observation about competition, events, or market — NO causal claim]
    — source: [API/dataset], operator interprets implication
  • …

🚫 (No "Recommendations" section in audit. Audit = observation. Action lives in a separate module per BoB persona EEC.)
```

**Why this is safer than SWOT:**
- **S** and **W** keep operator recognition.
- **O** and **T** are merged into **SIGNALS** with explicit "operator interprets" disclaimer → removes the speculation pressure.
- No "Recommendations" → forces audit to stay descriptive. Prescriptive output lives in a separate "Action" module (consistent with EEC: Bob extends the operator's cognition, doesn't replace it).
- Each bullet requires an inline source. Linter enforces.

**Recommendation:** **YES, but adopt "Evidence-First" not literal SWOT.**
